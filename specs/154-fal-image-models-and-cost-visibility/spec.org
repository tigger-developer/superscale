* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome

- The workspace offers a *searchable live FAL image catalogue*, shows the *selected endpoint's indicative cost*, and exposes *account balance and recent usage*.

** Before

- The app offers *only Grok Imagine* and shows a *fixed two-cent label*; pricing and account clients are present but disconnected from the GUI.

** After

- A native picker lists active image endpoints with *names, capabilities, IDs and details*; only endpoints whose request and response shape can be handled are selectable.
- Selecting an endpoint shows *live price or unavailable state* for the actual prompt-only or image-edit endpoint.
- A selection estimated above the *configurable USD $0.20 default* requires confirmation *at selection*; Apply makes *no further cost confirmation*.
- Settings shows *account balance, last-24-hour usage and recent billing events* using the existing separate account key.

** Changes

- Replace the one-entry model registry and fixed cost label with live catalogue, endpoint capability, pricing and selection state.
- Restore the non-secret cost threshold and connect the existing pricing and account services to the GUI.

** Unchanged

- *One working image* remains the only edit reference; filter selection is free, Apply is the paid action, and the CLI remains local-upscale-only.

** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:

- Missing or stale catalogue, unknown pricing, unsupported model schemas and billing-key failures have *visible, independent states*; none makes local upscaling unavailable.

** Decisions

- Use the provider's *catalogue and schema* for discoverability and eligibility; use the *actual submitted endpoint* for pricing and provenance.
- Treat an *unreliable or unavailable estimate* as requiring selection-time confirmation, as the product vision requires.

** Next step

- Definition review, then operator sign-off as described in [[#delivery-handoff][Delivery Handoff]].

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem

The app can already generate from a prompt or apply a filter to its working image, but the GUI exposes only one FAL model and a static price. Users cannot inspect other FAL image endpoints, compare their likely cost, or see account usage in the app. A published endpoint ID alone does not establish that the existing two-family request builder can submit to it.

** Outcome

For both prompt-only and working-image contexts, a user can search the live FAL image catalogue, inspect and select a compatible endpoint, see an endpoint-specific price state before paid work, and inspect account spending independently of generation.

** Scope

*** In scope

- Native model browsing and search, capability and compatibility presentation, endpoint-specific pricing, selection-time cost confirmation, and a configurable threshold.
- Account balance, last-24-hour usage and recent billing events in Settings; current-session estimated spend beside the paid action.
- Request and result handling for catalogue entries whose published schema fits the supported image contract, plus clear ineligibility for entries that do not.

*** Out of scope

- Multiple edit references, video/audio/3D models, non-FAL providers, user-authored payload forms for arbitrary schemas, and generation commands in the CLI.
- A second confirmation on Apply, a spending limit or quota, and a promise that an estimate equals the eventual billed charge.

*** Unchanged

- The graph remains the authority for the base, candidate, lock chain and held-result reuse. The existing two Keychain credentials retain separate roles.

** Constraints and dependencies
:PROPERTIES:
:CUSTOM_ID: constraints-and-dependencies
:END:

- Model metadata, endpoint availability, schemas and prices are *provider-owned and changeable*. Revalidate those contracts during delivery; do not encode a complete static catalogue or static prices.
- A generation key may access catalogue/pricing; usage and billing events require FAL =BILLING= permissions. A least-privilege billing-capable account key is sufficient; =FULL= is not required.
- All automated tests use injected transport and fixtures; any live FAL check is a bounded, operator-credentialed one-off or user test, never a persistent regression or build step.

** Decisions

- The model browser follows Pix's category-specific live search but uses native search and a detail pane. It does *not* copy Pix's 100-result first-page limit or its catch-all request payload: follow pagination and reject unhandled schemas before paid submission.
- The default remains Grok Imagine. The context determines whether the prompt-only or edit endpoint is offered; changing context does not silently replace a chosen endpoint.
- The threshold is a *per-request indicative estimate in USD*. Its default is =$0.20=, and the comparison is strictly greater than the threshold. A missing or unreliable estimate follows the vision's confirmation rule at selection.

** Unresolved blockers

- None.

* Edge Cases
:PROPERTIES:
:CUSTOM_ID: edge-cases
:END:

** Selection and context change

- Condition :: The user imports or clears a base image after choosing a model whose endpoint is incompatible with the new context, or a saved default is no longer offered.
- Required behaviour :: Keep the user's choice visible but mark it incompatible and disable Apply until the user chooses a compatible endpoint; suggest the Grok default without silently substituting it.
- Covered by :: [[#ac-154-1][AC154.1]], [[#ac-154-5][AC154.5]] and [[#rt-154-1][RT154.1]]

** Price changes after selection

- Condition :: FAL changes its price or the user changes the threshold after a model was confirmed.
- Required behaviour :: Show the latest fetched price and timestamp. A changed amount or threshold that would newly require confirmation makes the selection pending; confirmation occurs through model selection, never Apply.
- Covered by :: [[#ac-154-4][AC154.4]], [[#ac-154-5][AC154.5]] and [[#rt-154-4][RT154.4]]

** Partial account data

- Condition :: A later usage page or billing endpoint fails after balance succeeds.
- Required behaviour :: Keep successful subresults identified, mark incomplete totals or events unavailable, and offer retry; do not show a partial sum as the complete last-24-hour total.
- Covered by :: [[#ac-154-7][AC154.7]] and [[#rt-154-7][RT154.7]]

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context

- Relevant components :: =FalGenerationKit= owns FAL catalogue, schema eligibility, request and response handling, pricing and account HTTP; =SuperscaleUXCore= owns browser, selection, price, spend and account state; =SuperscaleApp= presents these in native controls.
- Ownership boundary :: SwiftUI never constructs provider payloads or reads secrets from persistence. The graph alone decides which image Apply can send.
- Existing pattern :: Extend the handler table and injected transport seams. Retain separate generation and account Keychain slots.

** High-level design

*** Catalogue and eligibility

- Query =GET /v1/models= for active =text-to-image= or =image-to-image= endpoints according to whether the graph has a base. Follow =next_cursor= to the end, deduplicate by endpoint ID and retain provider order. Request =expand=openapi-3.0= for the entries presented, or fetch schema on demand for a highlighted entry if a whole-page expansion is too large.
- A catalogue entry is selectable only when a deterministic adapter can build its required prompt and optional single-reference payload, omit unsupported optional controls, and parse an image result. Use explicit family adapters where necessary. Schema-derived admission may handle a plain =prompt= plus =image_url= or =image_urls= contract; any other required input, unsupported result shape, missing schema or unvalidated endpoint is displayed with a reason and is *not selectable*. No catch-all paid request is sent on a guessed payload.
- Show searchable display name, endpoint ID, category, description, tags and model link where supplied. A detail pane shows capability and eligibility, plus loading or unavailable states. A stale saved default or lost catalogue connection does not become an implicit new model.

*** Pricing and selection

- Price the *endpoint ID sent to FAL*, including edit endpoints. Request its unit price and historical per-call estimate through =FalPricingClient=. Show both with their actual currency and billing unit; the historical estimate is indicative, and the unit price alone is not treated as per-call cost when billed by megapixel, second or other variable unit.
- A candidate selection waits for pricing. Prefer FAL's historical one-call estimate; if it is unavailable, a flat per-image unit price for exactly one requested image can be used as a per-call estimate. Variable units, unsupported currencies and missing prices leave the estimate unknown. For a reliable USD estimate greater than the saved threshold, or no reliable estimate, present a confirmation naming the endpoint, estimate or uncertainty, and threshold. Accept commits the model; decline leaves the prior model. The default threshold is USD 0.20; store a finite nonnegative value in app preferences and expose it in Settings.
- The current selection retains its accepted price context. Refresh and context changes invalidate any newly risky acceptance, including an unconfirmed launch default. Apply reads the committed selection and has no cost dialogue; if selection is pending or incompatible, Apply is unavailable with an explanation and a route back to the picker.
- Replace the fixed cost label beside Apply with the live price/estimate or a clear unavailable state. Accumulate *estimated session spend* from successful new paid requests with known estimates only; count successful calls with unknown estimates separately. Never add a held result, rejected request, cancellation or failed request. Show currency and indicate this is not a billing ledger.

*** Account view

- Use the existing account key for =GET /v1/account/billing?expand=credits=, =GET /v1/models/usage= with explicit rolling 24-hour start/end and =expand=time_series=, and =GET /v1/models/billing-events?limit=20=. Follow usage pagination before publishing a complete total. Parse =cost_total= as the current field, retaining compatibility with =cost= only where FAL still supplies it. Show billed event =cost_total= rather than deriving it from units or the legacy nano-dollar estimate.
- Settings displays account identity and balance, last-24-hour usage estimate with its time window, and recent billed events with endpoint and timestamp. Sum usage only within the same currency; show separate totals if FAL returns more than one. Each subresult has independent loading, available and unavailable states. A missing key explains =BILLING= permissions. A 403 describes insufficient billing permission, not an undefined Admin scope.
- Account refresh is explicit and may also run after a successful paid request, without delaying the candidate image. The account key never substitutes for the generation key, and account failure never disables generation.

*** Data, failure and compatibility

- Persist the threshold and optional default model ID as non-secret preferences. Keep catalogue, price and account responses in memory only, with fetch time and endpoint identity; do not persist billing data. Validate stored defaults against the live catalogue before use.
- Cancel older catalogue and price tasks when context or highlight changes, and discard late responses by endpoint/context token. Expose retry for catalogue, pricing and account failures. Do not show stale pricing as current for another endpoint.
- Keep the existing Grok request path and Graph result handling. New adapters must preserve one-reference editing, prompt-only generation, current cancellation semantics, output download, redaction and existing local-upscale behaviour.

** Design decisions and verification

*** Live discovery with guarded execution

- Decision :: The browser is broad; paid execution requires an eligible schema or explicit adapter.
- Rationale :: FAL's live catalogue is larger and more variable than Pix's handler fallback or Superscale's two-entry table. Guessing an arbitrary payload could misrepresent compatibility or incur an unintended request.
- Verification :: [[#rt-154-1][RT154.1]], [[#rt-154-2][RT154.2]] and [[#ut-154-1][UT154.1]].

*** Confirmation belongs to selection

- Decision :: Price and uncertainty are reviewed when selecting the model. Apply is a single paid-action control with no cost dialogue.
- Verification :: [[#rt-154-4][RT154.4]] and [[#rt-154-5][RT154.5]].

*** Actual billing and estimates stay distinct

- Decision :: Per-call pricing, session estimate, usage estimate, credit balance and billed events are separate labelled values.
- Verification :: [[#rt-154-3][RT154.3]], [[#rt-154-6][RT154.6]] and [[#ut-154-2][UT154.2]].

** Routine details left to implementation

- Native layout of the search field, result list and details pane within the current workspace; SwiftUI component boundaries and non-material cache duration.

** Architecture impact

*** Security impact

- Threat boundary :: Existing generation-key and billing-key trust boundary remains; only FAL's HTTPS platform and generation endpoints are contacted.
- Data and secrets :: Keys remain in Keychain and headers; redact both keys from diagnostics. Billing responses stay in memory and are excluded from session files and app bundles.
- Access :: Ask for the least-privilege =BILLING= key for usage and events; no automatic credential reuse or privilege widening.
- Conclusion :: Existing FAL transport and redaction patterns extend to catalogue and pricing; newly displayed account data needs explicit in-memory lifetime and no log exposure.

*** Other relevant qualities

- Accessibility :: Search results, eligibility, price state, threshold and confirmation must be reachable and named through native keyboard and VoiceOver controls.
- Reliability :: Pagination, cancellation and independently recoverable failures prevent a partial catalogue or account total from being represented as complete.
